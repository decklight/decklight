Math, Rendered Native

data-math + LaTeX → MathML Core — no webfonts, no build step, no network

$$\begin{aligned} \nabla \cdot \vec{E} \;&= \frac{\rho}{\varepsilon_0} & \nabla \times \vec{E} \;&= -\frac{\partial \vec{B}}{\partial t} \\[0.5em] \nabla \cdot \vec{B} \;&= 0 & \nabla \times \vec{B} \;&= \mu_0 \Bigl( \vec{J} + \varepsilon_0 \frac{\partial \vec{E}}{\partial t} \Bigr) \end{aligned}$$

Inline math sits in the sentence — light moves at \(c = 1/\sqrt{\mu_0 \varepsilon_0}\) — while \$ keeps \$5 five dollars, and a lone $ never trips the parser.

Academic decks, welcome home. Mark a slide data-math and write LaTeX — double dollars for display, backslash-parens for inline. That's Maxwell, all four, rendering as native MathML: no webfonts shipped, no network fetched, no per-deck build step. And note what is deliberately not supported — the single dollar sign. Your prose about a five-dollar budget stays prose. The parser only listens where you actually meant math.

Marketplaces: Registered, Not Fetched

A marketplace is a git repo with a manifest at its root. There is no central registry.

  • decklight marketplace add owner/repo — clones a catalog with your own git credentials, so a private one works; entries install from that clone, never from a second fetch
  • So a deck on a plane behaves exactly like a deck at a desk — list reads the cache and names what it couldn't read, rather than showing an empty list that looks like an empty marketplace
  • The first-party catalog is registered on first run and never auto-fetched — the homage theme packs live there
  • Units: themes · templates (init --from) · agent skills · import adapters · publish targets · voices

Now distribution at scale. A marketplace here is just a git repo with a manifest file at its root — decentralized, mirroring Claude Code's own layout deliberately. There's no central registry to host or moderate.

⟨CLICK⟩

Extensions Run at Build Time

The decision that keeps a travelling deck safe

Build-time transform

Node, on your machine, during bundle. HTML in, HTML out. Mermaid, PlantUML, new chart types — all compile to SVG before anyone opens the deck.

Only its output travels.

In-deck runtime

Would run in the audience's browser — someone who installed nothing and consented to nothing.

Deliberately not shipped. The first cut has no in-deck execution surface at all.

Extensions are where most plugin systems quietly become a security problem, so this one starts from an asymmetry. Claude Code's plugin marketplace is safe enough because the person who installs a plugin is the person at risk — their machine, their privilege, their choice. A deck breaks that symmetry, because a deck travels. Code inlined into it runs in front of an audience that installed nothing.

⟨CLICK⟩

So the default is a build-time transform: Node code that runs on your machine during bundle, taking HTML and returning HTML. Mermaid diagrams, PlantUML, alternative renderers — they all compile to SVG before the file ever leaves, and the audience's browser executes nothing new. Only the output travels.

⟨CLICK⟩

And the in-deck runtime — code that would execute in the viewer's browser — is deliberately not shipped. Not deferred because it was hard; refused because the first cut should have no such surface at all. If a live case ever justifies it, it arrives with Worker isolation, a CSP allowlist and consent at first open.

Decks travel — that breaks the plugin trust model

The Admission Gate

decklight extension check transform.mjs — what a marketplace's CI runs before merging your submission

  • Lint the source — no fetch, no eval, no XMLHttpRequest, no dynamic import(). Advisory: it catches the honest mistake — the submission never executes in the checker's own process, but behind a locked-down child
  • Headlessly load its OUTPUT against a randomised fixture — and refuse any <script> or inline on…= handler in the result. The one automatable proof that "nothing executable travels" actually holds for a given transform
  • Not run by bundle or publish: the gate sits at the marketplace's door, once, not on every local iteration

And a rule nobody checks is a wish, so there's a command that checks this one.

⟨CLICK⟩

First it lints the source for network and dynamic-code calls. Be clear-eyed about what a lint is, though: it catches the honest mistake, not a determined one — a static child_process import sails right past a regex. So the check never runs the submission in its own process. It runs it in a separate Node process under the permission model: no file writes, no child processes, a scrubbed environment, a hard kill. The screen is the lint; the enforcement is the boundary.

⟨CLICK⟩

Then it runs the transform against a small randomised fixture — randomised so a submission can't recognise the checker and behave just for it — and headlessly loads what came out, refusing any script block or inline handler in the result. That's the automatable proof that this specific transform honors 'nothing executable travels' — rather than merely having been asked to.

⟨CLICK⟩

And it deliberately isn't part of bundle or publish. An installed transform you use every day is never re-checked; the installer bears that risk, and the gate is at the marketplace's door, once.

A rule nobody checks is a wish

Playing a Deck You Didn't Write

decklight present — read-only over localhost, under a real CSP header

  • An ingredients label before the first slide: the runtime's hash against the build you have, and every unaccounted script by line number
  • An inventory, never a verdict — no green check, because a check promises more than a heuristic can keep
  • --strict strips every script that isn't the verified runtime — and the deck still plays
  • The audit runs because it is the only way in — a standalone verify is a step people skip

A deck arrives on machines belonging to people who agreed to nothing, so there's a command for playing one you didn't write. It serves the file read-only over localhost under a real CSP — an HTTP header, which the document cannot override, unlike a meta tag inside a file an attacker may have edited.

⟨CLICK⟩

Before the first slide renders it prints an ingredients label: which runtime is embedded and whether its hash matches the build this install ships, the counts of inert data, and then every script block it could not account for, with line numbers and opening lines.

⟨CLICK⟩

And it refuses to print a verdict. No green check, no score. It's a heuristic reading a file someone may have edited, and a green mark would promise more than the mechanism can keep. A list of what will run promises nothing and is still what you needed.

⟨CLICK⟩

Strict mode strips every script that isn't the verified runtime, and the deck still plays — because a well-formed decklight deck carries no third-party JavaScript in the first place. Content is HTML, themes are CSS, charts and casts are JSON read by trusted code.

⟨CLICK⟩

And the audit runs because it's the only way in. A standalone verify command is a step people skip; folding it into the command you'd use anyway means it runs every time at no extra effort.
